In dtrace probes comes from providers, which are kernel modules. Dtrace causes no performance degradation because whole dtrace environment is dynamic, there is no instrumented code when probes are inactive.
The naming pattern is 
```bash
provider : module : function : name

BEGIN probe true name is dtrace:::BEGIN
```

Provider : The name of the DTrace provider that is publishing this probe. The provider name typically corresponds to the name of the DTrace kernel module that performs the instrumentation to enable the probe.
Module : If this probe corresponds to a specific program location, the name of the module in which the probe is located. This name is either the name of a kernel module or the name of a user library. 
Function : If this probe corresponds to a specific program location, the name of the program function in which the probe is located. 
Name : The final component of the probe name is a name that gives you some idea of the probe's semantic meaning, such as BEGIN or END. 

Try executing :
```bash
# In NetBSD/Illumos load the modules(mostly builtin) - either root, sudo , doas or pfexec
modload solaris
modload dtrace

dtrace -l
dtrace -l | wc -l
dtrace -n BEGIN -n END
```
-> Compilation and Instrumentation
Once experiment completes and dtrace command exits, all probes are automatically disabled and the instrumentation is removed.
DTrace D programs are compiled into a safe intermediate form that is used for execution when your probes fire. This intermediate form is validated for safety when your program is first examined by the DTrace kernel software. The DTrace execution environment also handles any run-time errors that might occur during your D program's execution, including dividing by zero, dereferencing invalid memory, and so on, and reports them to you.
As a result, you can never construct an unsafe program that would cause DTrace to inadvertently damage the illumos kernel or one of the processes running on your system. 
So if programming mistakes are made, dtrace reports the error to you.
